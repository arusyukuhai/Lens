# Lens / Replacer コード監査・修正報告 — 2026-10-07

対象: `アーカイブ 5.zip` の現行通常GA版 `main.py` / `gpu_replace_persistent.py`

現行コードには、単なる微最適化ではなく、学習内容・resume後の選択・長時間運転・MPS側の実行量に影響し得る問題が複数あった。通常GAという現在の設計は維持し、差分進化経路の廃止は仕様として扱った。

修正版の検証結果:

- `pytest -q`: **46 passed, 4 skipped**。4 skip は廃止済み差分進化専用テストのみ。
- `python main.py --self-test`: **PASS**
- `validate_recode_memo.py`: **PASS — 100k translated memo contracts + sentinels**
- `validate_crossover_share.py`: **PASS — 1000 same-embedding crossovers allocate no recoded donor Rules**
- Python構文検査: PASS
- CPUの短い学習・checkpoint/resume smoke test: PASS
- 実checkpointのv3保存→再読込構造一致: PASS

Metal/MPSの実機コンパイル・実行だけは、このLinux実行環境では検証できない。MetalソースとPython側オーケストレーションは静的検査・既存reference evaluatorテストまで確認した。

## 修正した問題

### 1. 長いコーパス断片がcropされる前に捨てられていた — 学習データ欠落

`load_local_corpus()` と `stream_github_code()` で、従来は `len > max_len` を先に `continue` していたため、その後にあるcrop処理へ到達できなかった。つまり「長文を上限長へ切って使う」つもりが、実際は長文を丸ごと捨てていた。

さらに `max_len=0` を無制限として扱うべき経路でも、従来条件では非空データがほぼ全拒否され得た。

修正: 最小長だけ先にrejectし、`max_len > 0` の場合だけ超過分をcrop。`max_len <= 0` は上限なし。

影響: 訓練分布そのものを歪めるため重要度は高い。

### 2. 推論GAの突然変異個数が指定済みlog-uniform仕様から退行

`sample_inference_mutation_count()` が、70%で1個固定・20%で2–4個・残りだけ広域というlocal-heavy方式へ戻っていた。これは以前指定された

`round(exp(uniform(0, log(k))))`

と異なり、探索半径を強く局所へ偏らせる。

修正: 全域でlog-uniform半径へ復帰。focus locusは必ず含めつつ、半径そのものは1へ潰さない。

影響: `inferBest` / repair探索の到達性に直接関係する。

### 3. standalone推論予算resolverの互換性退行

`resolve_inference_budget()` を単独利用した場合にも「1 genome」と仮定してgeneration数まで縮めており、公開関数として以前の挙動と不整合だった。

修正: 実訓練が明示的にgenome geometryを渡す場合は現行のwidth-first予算制御を維持し、geometry省略時のみstandalone互換動作にした。

実訓練の既定planは従来どおり約 `3 x 16 x 29` で、work capも維持。

### 4. resume直後のHoF scoreとplateau判定が古いrolling setを引きずる

rolling evaluation serialはresume後に再生成される一方、checkpoint内HoFの古い `fitness` / scoreを現在caseの値として扱える経路があった。また旧履歴からPlateauTrackerを再構築すると、別rolling setの値を現評価と連結して停滞判定してしまう。

修正: resumeしたHoFは構造・embedding・履歴メタ情報のみ保持し、現在case依存の `fitness`, `case_scores`, `readout_weights`, eval serialを未評価状態へ戻す。PlateauTrackerもresume地点から新たに開始する。

HoF近傍重複処理も、未再評価incumbentが古いscoreだけで新候補を拒否しないようにした。

影響: resume後の選択圧・停滞判定の正しさに関わる。

### 5. HoFがRuleを全deep copyしており、長期運転でPython負荷・RAMが急増

1500 RuleのGenomeをHoFへ入れるたびに全Ruleをdeep copyしていた。通常のmutation/crossover経路を監査すると、構造変更対象Ruleは変更前にcloneされるため、Rule構造はCOW共有できる。

修正: HoF保存、HoF親、注入等をshallow/COW化。書き換え経路が共有Ruleを破壊しないことをテスト。

合成ベンチ（1500 Rule個体を300回clone）:

- COW shallow: 約 **0.0017 s**
- deep copy: 約 **0.433 s**

clone部分だけなら約250倍の差。特にHoF利用頻度が高い長期runで有効。

### 6. HoF近傍距離判定が archive_size × rules の全走査

`update_hall_of_fame()` は各候補についてHoF全件との完全な `genome_structural_distance()` を計算していた。`hof-size=16384`, `rules=1500` では1候補だけでも非常に大きいPython走査になる。

修正: `genome_structural_distance_below()` を追加し、「min_distance未満か」という必要な判定だけならlower boundで早期終了。閾値付近だけ完全距離を計算する。

ランダム500ケースで完全距離判定との意味的一致を確認。1200 archive ×1500 rulesの合成測定では約 **0.176s → 0.0295s**、約6倍。

### 7. MPS rule-pool GCのrootにHoF全体を含めていた

従来はGC時にpopulationだけでなくHoF全体をrootにしていた。HoF上限16384では、GCの生存参照数が最大約2458万Rule参照に達し、ratio-based GCが発火しにくくなるうえ、発火時のtraceも巨大になる。

実履歴の直近200点でも `pool_rules` median約540k、p90約871k、max約977kに対し `pool_gc` はmedian/p90とも0だった。

修正: GC rootを「現在実際に評価中のGenome群」に限定。GCのたびにpool owner epochを更新し、root外にあるHoF Ruleの古いpool idは次に使われる時に安全に再internされる。

### 8. GC epoch導入時にeval signatureが構造hashへ退化する隠れ性能バグを予防修正

評価重複除去のsignature計算がpool ownerを `id(mps_evaluator)` と固定していた。GCでowner epochを変える修正だけ行うと、GC後の全Ruleでpool-id fast signatureが使えず構造hashへ退化する。

修正: signature生成側も常に現在の `mps_evaluator._pool_owner` を参照。

### 9. hidden-memory Metalカーネル内にO(pair_count²) prefix scan

hidden rewrite phaseで各pairごとに `gp_hidden_item_start()` が先頭から長さ配列を再走査しており、pair_count分のprefix sumを毎回作り直していた。最大pair数は小さくても、phase × rounds × jobsで繰り返すためMPS dispatch内部の純粋な無駄。

修正: phase内は左右それぞれrunning offsetを維持してO(pair_count)化。またopcodeがアクセスするtop/bottom first/secondは総長と端のlengthからO(1)で位置計算し、将来の一般indexだけfallback scan。

CPU側意味論は変更していない。

### 10. checkpointが同じRule構造をGenomeごとに重複保存

旧形式はpattern/replacement token列を各Genome・各Ruleについて繰り返し保存。HoF拡大時にcheckpointが急激に肥大化する。

修正: checkpoint v3でRule構造をdedupし、Genome側は `rule_refs` を保存。旧v1/v2読込互換を維持。

重要: RuleのMPS anchor/filter cacheはembedding依存なので、共有範囲を「同じembedding座標系」に限定。同じ文字列Ruleでもembeddingが異なるGenome間では同一Rule objectへ統合しない。

### 11. HoF checkpointにresume後すぐ捨てる巨大な一時状態まで保存

HoFの `readout_weights`, 現rolling case score等はresume時に再評価するので、保存しても使用しない。HoF満杯ならweightsだけで概算 `16384 × 1500 × 4 ≈ 98 MB`。

修正: HoFは構造・embedding・必要なメタ情報だけ保存し、一時的学習状態は省略。population/bestには従来どおり必要状態を保存。

手元の実checkpointで:

- 元: **30,402,694 bytes**
- v3再保存: **9,755,314 bytes**
- 約 **68%削減**

再読込後の構造一致を確認。

### 12. `seconds` が実際の世代wall timeを過小表示

従来の `seconds` はbreeding・plot・checkpoint等より前に確定していたため、ログだけ見ると本当のボトルネックを見誤る。

修正: 既存CSV互換のため `seconds` はcore時間として残し、追加で `core_seconds`, `breed_seconds`, `wall_seconds` を記録。breeding後にCSV/plotへ反映する。

checkpoint時間は従来どおり別表示。

## 意図的に変更していない設計上の論点

1. `hof-size=16384` は修正後も大きい。COW化でRule本体の複製は避けたが、満杯時には `16384 × 1500 ≈ 24.6M` 個のPython参照をrules listだけで持つため、おおよそ200MB級の参照領域になり得る。さらに1世代128 HoF評価なら全HoFの平均更新周期は約128世代。研究意図がなければ2k–4k程度へ落とす余地が大きいが、探索挙動を変えるため自動変更はしていない。

2. pairwise rank-ridge readoutを、outer Spearmanを測る同じtrajectory集合でfitしている。従ってouter fitnessはreadoutに対してin-sample。コード内の `audit_generalization.py` がfrozen-readout監査を持つので、これは意図的objectiveとして維持した。汎化性能を直接選択圧へ入れたいならtrain/eval trajectory splitを別途設計すべき。

3. inferenceのwork capは「model-job相当量」であり、実wall time上限ではない。実履歴の `inference_time_ratio` は直近200でmedian 0.888、p90 1.278。短いouter trajectoryと長いinference trajectoryの組合せ等で0.75相当jobでも時間比は0.75を超え得る。時間依存adaptive budgetは再現性を弱めるため今回は入れていない。決定論を保つならtoken長・round見積り込みの静的budgetが次の候補。

4. 差分進化専用の旧テスト4件は、現在の通常GAへの復帰方針に合わせてskip化した。ただし通常GA内の3-parent diff/git-style crossover自体は既存の交叉手段の一つとして残している。

## 推奨する次の計測

修正版で実機MPSを100–300世代走らせ、追加した `core_seconds / breed_seconds / wall_seconds` と既存の `mps_dispatch_seconds / inference_seconds / pool_rules / pool_gc` を比較すると、今回の構造修正後に次に手を入れるべき箇所が明瞭になる。特にGCが実際に発火した後もdispatch前後のsignature処理が増えないこと、HoFが数千件へ伸びてもbreed/wall timeが線形悪化しないことを確認するとよい。
